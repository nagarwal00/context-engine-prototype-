# Known Limitations & Honest Scope Disclosures

In accordance with academic integrity guidelines for UCS503 Capstone, this document honestly lists the current boundaries, constraints, and known limitations of the Context Intelligence Framework (CIF).

---

## 1. WhyBench is Synthetic; Results Show Internal Consistency, Not Generalisation to Real Repositories

- WhyBench-Synth consists of hand-authored synthetic event sets created by the team to test decision reconstruction, lifecycle state tracking, evidence grounding invariants, AST resolution, and negative abstention.
- Project identifiers (`acme-ecommerce/payment-core`, `cloud-hypervisor/cloud-hypervisor`, `cli/cli`) are used solely as realistic domain labels. No event, quote, author handle, or PR/issue number is claimed to exist in real project history, and source URLs are illustrative mock citations.
- Consequently, evaluation demonstrates internal algorithmic consistency, lifecycle state transitions, and abstention behavior on curated scenarios; it does **not** demonstrate generalisation to uncurated real repositories with ambiguous or unstructured discussions.

---

## 2. Synthetic Pilot Repositories (Smoke Tests Only)

- The pilot repositories `acme-eng/thermal-control-system` and `acme-eng/distributed-cache-service` are synthetic datasets created by the project team.
- They serve strictly as **smoke tests** to verify that the database invariants, temporal graph traversal, AST entity resolution, and UI rendering function end-to-end.
- Performance numbers on the pilot repositories do not represent generalizable extraction accuracy; benchmark performance is evaluated on WhyBench-Synth (§1).

---

## 3. WhyBench-Synth Benchmark Corpus Scope

- WhyBench-Synth evaluates 3 synthetic domain repositories (`acme-ecommerce/payment-core`, `cloud-hypervisor/cloud-hypervisor`, `cli/cli`) with a total of **134 labelled questions** (63 dev split, 71 `test_v2` split).
- While every question is designed with strict criteria to test decision reconstruction or refusal, evaluating large-scale uncurated repositories across diverse programming languages (e.g., C++, Java, Rust) remains future work.

---

## 4. Extraction Accuracy & Recall Boundaries

- All empirical extraction and baseline metrics are dynamically measured by the WhyBench runner; see [evaluation_results.md](evaluation_results.md) for current generated values.
- The system prioritizes **precision over recall**: it indexes decisions with explicit architectural markers or structured ADR records, achieving high state accuracy and reliable refusal on negative queries, but naturally misses decisions discussed casually in PR comments without structured phrasing.
- Unstructured keyword search (Baseline A / BM25) achieves higher raw event hit rates on retrieval (24/26 = 92.3% vs CIF 21/26 = 80.8% on the 26 positive questions), but lacks any refusal capability and cannot distinguish accepted from rejected decisions. CIF's core value is state classification (100% accuracy on matched decisions), abstention on unrecorded questions (64.4%), and guard-rule enforcement.
- **Refusal & Abstention Boundaries**: On negative questions regarding unrecorded architectural topics (45 questions in `test_v2`), the system correctly abstains on 29/45 (64.4%) by outputting "No recorded architectural decision found". On 16/45 (35.6%) of unrecorded cases, the system emits an ungrounded or unsupported decision candidate due to heuristic token overlap with unrelated repository context. Grounding invariants prevent saving decisions without evidence in the graph, but question-answering retrieval abstention remains a key area for calibration improvements.

---

## 5. Unmeasured Baseline Systems

- **Baseline C (Plain LLM over Repository Context)**: Not measured in the default offline distribution because it requires an external API key (`CIF_LLM_API_KEY`). The LLM client interface is implemented, but numbers are reported honestly as `not measured` when keys are omitted.
- **Baseline D (GitHub Copilot)**: Automated testing of proprietary IDE chat assistants is not supported via open CLI APIs. A template (`manual_copilot_results.csv`) is provided for future human trials.

---

## 6. GitHub App Live Integration Scope

- The GitHub App webhook receiver (`/api/webhook/github`) and PR feedback commenting pipeline are fully implemented and verified with cryptographic HMAC-SHA256 signature fixtures in `tests/test_webhook.py`.
- However, live execution against active production GitHub repositories has not been deployed due to network and tunnel constraints in the student lab environment. Detailed manual setup instructions are documented in `GITHUB_APP_SETUP.md`.

---

## 7. GitHub Pages Static Snapshot vs. Live Server

- The deployed GitHub Pages demo runs entirely in the browser using a static snapshot generated by `tools/build_static.py`.
- Running the live Python engine requires starting `python server.py` locally or deploying the containerized backend using `Dockerfile`. A visual badge in the dashboard header clearly indicates whether the UI is communicating with the `Live engine` or using a `Static snapshot`.

---

## 8. Slack Ingestion Scope: Offline Workspace Exports Only

- Live Slack API bot connectors (WebSockets / real-time event subscriptions) are omitted from runtime scope because live enterprise Slack workspace tokens and admin permissions were not provisioned.
- CIF provides a dedicated offline export adapter (`backend/ingestion/slack_adapter.py`) that ingests standard Slack workspace export directories (`users.json`, `channels.json`, and daily per-channel message logs).
- Slack messages are mapped to `Event(source_type="slack_message")`, grouped by conversation thread for source independence analysis (`slack_thread:<channel>:<thread_ts>`), resolved through `IdentityResolver`, and rigorously scrubbed by the privacy sanitizer before SQLite persistence.

---

## 9. Hold-Out Dataset Scope & Code-Identifier Dependency

- The hold-out drift evaluation set (`backend/evaluation/holdout/`) demonstrates 100% precision and recall (16/16 cases) on synthesizing guard rules from architectural decisions in a third independent domain (`acme-eng/job-queue-service`).
- **Limitation**: This mechanism relies on explicit backticked code identifiers, module names, or import tokens in the rationale text (e.g., `` `celery` ``, `` `zeromq` ``, `` `pickle_serializer` ``).
- Synthesizing active lint rules from unstructured, natural language prose devoid of code tokens remains uncalibrated and is acknowledged as an ongoing research boundary.

---

## 10. Positioning Relative to Related Paradigms (Continuum, Warrant, Context Graph)

- **Continuum (Architectural Knowledge Evolution)**: Research frameworks like Continuum focus on passive, post-hoc mining of architectural tactics from commit logs. CIF departs from this by introducing an *active mechanical grounding invariant* that prevents unevidenced decisions from entering the graph and performs active pre-commit drift interception.
- **Warrant (Argumentation & Justification)**: Grounded in Toulmin's argumentation model, warrants connect contextual constraints to architectural patterns. CIF reifies warrants into concrete, traversable evidence edges linking decisions to commits, issues, and PRs, surfaced directly in developer tools (Chrome and VS Code extensions).
- **Context Graph (Operational Enterprise Context)**: Unlike enterprise context graphs requiring heavyweight distributed graph databases (e.g., Neo4j, TigerGraph), CIF implements in-process temporal graph resolution directly over standard-library SQLite, achieving sub-15ms query latencies suited for local developer environments.
