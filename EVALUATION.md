# Context Intelligence Framework (CIF) — Evaluation Methodology & Benchmark Guide

This document describes the evaluation framework, dataset splits, baseline comparisons, calibration analysis, and exact reproduction instructions for the Context Intelligence Framework (CIF).

---

## 1. Honest Experimental Scope

In accordance with rigorous academic integrity:
1. **Pilot Repositories are Synthetic**: The pilot repositories (`acme-eng/thermal-control-system` and `acme-eng/distributed-cache-service`) are synthetic datasets designed strictly as end-to-end integration smoke tests for graph traversal, temporal validity, and AST entity resolution. They are **not** evaluation benchmark results.
2. **Benchmark Ground Truth (WhyBench)**: Benchmark claims are evaluated against **WhyBench**, an open benchmark comprising 3 repositories (`acme-ecommerce/payment-core`, `cloud-hypervisor/cloud-hypervisor`, and `cli/cli`).
3. **No Hardcoded Metrics**: All empirical metrics in this project are dynamically measured and generated by running `tools/run_whybench.py`. For the measured metrics, see [evaluation_results.md](evaluation_results.md) and the JSON manifests in `results/`.
4. **Heuristic Confidence Scores are Uncalibrated**: Confidence values produced by rule-based heuristic weights are explicitly labelled **"uncalibrated"** in the dashboard and evaluation reports until validated by empirical human-labelled reliability diagrams (ECE).
5. **Webhook/CI Verification**: Automated webhook HMAC-SHA256 signature and CI checks are verified with mock fixtures (`tests/test_webhook.py`). Live production webhook operation requires an external tunnel/IP per `GITHUB_APP_SETUP.md`.
6. **GitHub Pages Deployment**: The deployed GitHub Pages demo is a static snapshot generated by `tools/build_static.py`. It reflects a point-in-time database snapshot with an explicit SHA-256 hash and generation timestamp.

## 2. Benchmark Task Definitions

WhyBench formally evaluates two distinct tasks to prevent comparing unlike systems directly:

### Task 1: Evidence Retrieval ("Find the sources that explain X")
- **Input**: Natural language architectural query string + repository identifier.
- **Systems Evaluated**: Comparable across CIF and baseline search algorithms (Baseline A: Keyword/BM25 token overlap; Baseline B: Documentation/ADR search).
- **Metric**: Top-$k$ ($k=5$) evidence event hit rate (percentage of queries where at least one ground-truth evidence event ID is present in top 5 retrieved items).
- **Fair Comparison (Positives Only)**: When scored fairly on the exact same 26 positive questions (`expected_state != 'none'`), Baseline A (BM25) achieves **92.3%** (24/26) and Baseline B (Docs-only) achieves **23.1%** (6/26) vs CIF's **80.8%** (21/26) decision-evidence match.
- **Footnote**: *CIF's metric is decision-evidence match, not ranked retrieval; BM25 retrieval is higher. CIF's value is state classification, abstention and guard rules (see Task 2).*
- **Refusal**: Unconditional top-$k$ search baselines have no refusal mechanism; they are explicitly marked `n/a (always answers)` rather than scored 0.0%.

### Task 2: Decision Reconstruction (State, Rationale, Alternatives, Supersession)
- **Input**: Full repository event stream and git diffs.
- **Systems Evaluated**: CIF (reconciled state machine, structured candidate extraction, context graph) vs Baseline C (LLM) / Baseline D (Copilot) when configured.
- **Metrics**: Strict one-to-one decision recall (bipartite greedy matching), decision state accuracy, grounded rationale & alternatives, and refusal accuracy on negative cases.
- **Measured Outcomes (`test_v2`)**: CIF achieves **80.8%** (21/26) Strict Recall, **100.0%** (21/21 matched decisions, small n) State Accuracy, and abstains correctly on 29/45 (64.4%) of unrecorded-topic questions (16/45 receive an unsupported decision — see LIMITATIONS).
- **Non-reconstructing Baselines**: Baseline A and B cannot extract decisions or lifecycle states; their Task 2 metrics are marked `n/a` rather than 0.0%.

## 3. Dataset Splits & Freezing Policy

| Split | Description | Purpose | Execution Policy |
|---|---|---|---|
| **`dev`** | 18 standard questions + 6 negative cases across 3 repositories | Threshold tuning, recall failure analysis, rule iteration | Unlimited runs; monitored via `tools/analyze_failures.py --split dev` |
| **`test_v1`** | Historical baseline split | Pre-improvement baseline comparison | Frozen baseline reference |
| **`test_v2`** | 20+ verified questions per repository | Headline evaluation | **Strictly frozen**: SHA-256 recorded in `whybench/FROZEN.md`. Executed only once with `--final` |

## 4. Failure Analysis & Error Categorization

When analyzing missed ground-truth items on `dev`, `tools/analyze_failures.py` assigns each miss to exactly one root cause category in strict priority order:
1. `not_ingested`: Expected evidence event ID absent from SQLite `events` table.
2. `no_candidate`: Event present in database, but extractor produced 0 candidates from its bundle.
3. `filtered`: Candidate produced, but discarded by a quality/noise threshold.
4. `wrong_evidence`: Decision exists in repository for overlapping entity, but cites different events.
5. `wrong_state`: Found decision with matching evidence, but system state differs from expected state.

## 5. How to Reproduce All Results

### Step 1: Initialize Database & Seed Pilot Data
```bash
python tools/init_db.py --seed --fresh
```

### Step 2: Run Development Benchmark Suite
```bash
python tools/run_whybench.py --split dev
```

### Step 3: Run Failure Analysis Tool
```bash
python tools/analyze_failures.py --split dev
```

### Step 4: Run Secret & Security Scanner
```bash
python tools/scan_secrets.py
```

### Step 5: Run Full Test Suite
```bash
python -m unittest discover tests/
```

### Step 6: Verify Demonstration Pipeline
```bash
python run_demo.py
```

### Step 7: Build Static Snapshot for Deployment
```bash
python tools/build_static.py
```
